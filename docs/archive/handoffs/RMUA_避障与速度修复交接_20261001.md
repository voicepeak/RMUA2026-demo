## 2. 当前真正的卡点：为什么避障这么慢

### 2.1 规划有效期直接触发停车，已经有日志实证

文件：`repo/ros_ws/src/route_follower/scripts/route_follower.py`，约 947 行：

```python
planned = self.clearance_info.get('planned_stamp')
if planned is None or pose_stamp - planned > .7:
    self.clearance_info = dict(self.clearance_info, cap=0., stale=True)
```

即使上一条轨迹被标为 `feasible=True`，只要生成时刻超过 0.7 秒，也会被硬限速到 0。它没有先用最新点云快速检查“正在执行的短段轨迹是否仍安全”。

最新 run15 返程的真实日志例子：

```text
s=125.085
pose_stamp=1790788422.1117938
planned_stamp=1790788421.292776
age≈0.819 秒
feasible=True
selected_clearance=1.768 m
planning_ms=126.924
stale=True
cap=0
speed=0
```

这不是“YOLO没看见车”：该次规划已经有可行路径，最终被有效期规则停下。这里 `planning_ms` 只记录该条已完成任务的耗时，不代表下一条任务的耗时；排队、正在计算的新任务、控制读取延迟和时钟关系都需要分开分析。

更晚的最后一条遥测：

```text
s=132.607642
speed=0
clearance: feasible=False, cap=0, stale=True
source=PREDICTIVE, cars=10
planning_ms=1109.817
pose_stamp=1790788885.0006685
planned_stamp=1790788883.7826424
```

最后一条已处于后续结束时段，不能据此还原最终裁判原因。不过它能证明代码仍在反复产生超过有效期的规划结果。

返程整段采样中曾记录到最高约 8.53 秒的 `planning_ms`。该统计包含结束后的停滞样本，且同一规划会被多条遥测重复记录，**不能直接当作有效比赛内独立任务的 P99**。接手时应先限定比赛有效时间，再按 `planned_stamp` 去重。

### 2.2 复杂场景下的搜索量仍然很大

`predictive_avoidance.py` 的当前做法：

- 每次最多 65 m 前视；先试多个横向/高度偏移以及不同进入长度的五次曲线。
- 常量偏移通不过时，进入 `lattice_detour.py`：每米一个截面、每个截面 91 个 `(横移, 高度偏移)` 状态。
- 格点转移还做多点净空检查；平滑后再稠密验证。
- KDTree 已替换部分暴力距离查询，规划已搬到单独线程，但这些改动没有消除最坏耗时。
- 只有一个后台任务；旧任务未完成不会提交新任务。场景复杂时，结果可能还没拿到就已超过 0.7 秒的有效期。

所以“异步”解决的是主控制循环等待问题，并没有自动解决计划过期、最坏计算时间以及 Python/CPU 争用。

### 2.3 格点轨迹不保证平滑回到原路线，存在明确实现缺口

`lattice_detour.py` 的末端选择仅有弱代价：

```python
end = argmin(previous + .3 * sum(offsets * offsets))
```

它没有强制末端偏移回到零，也没有保证终端横向/高度导数为零。`LatticeDetour.end` 只是规划窗口的末站；`SpatialCurve` 超出范围后延续最后一个值。

run15 早期实际执行的某条格点轨迹：

```text
start≈22.173, end≈87.173
target≈[-0.6006, +1.5]
当前偏移≈[-0.5007, +1.5]
```

这里 **NED 坐标 z 越大越低，`vertical=+1.5` 表示向下偏移 1.5 m**，不是抬高 1.5 m。长时间向下偏移可能使门框下沿和道路底部净空变差。

另一个分支在名义路线被判为可行时，直接 `self.plan=None`。若上一条轨迹还有非零偏移，清空轨迹后的参考就可能发生跳变。规划器有些地方用旧轨迹的偏移作为新轨迹起点，控制器又在其他分支单独滤波偏移；需要检查**被认证的轨迹和飞机实际跟踪的参考是否相同**。

**已确认：末端回中约束缺失、直接清空轨迹的分支存在。尚未证明：它们分别贡献了多少次现场急停。** 上一轮尚未修复这一点，用户即要求停止。

### 2.4 门洞、道路和飞行动力学没有被完整统一约束

常量偏移候选对计分门偏离只是加罚分，阈值为横向/高度各 1 m，不是基于实际门洞尺寸、机体大小和跟踪误差的硬约束。

格点搜索没有接收门洞列表，主要靠点云净空。它不能保证未来每个必须穿的门都在飞机可执行的轨迹上。

几何曲线可行也不等于飞行可行。目前分别计算坡度、曲率、跟踪误差、障碍、可见距离等速度上限，缺少统一的三维轨迹时间参数化。重规划切换时的速度/加速度连续性尤其需要检查。

另外，当前净空约 1.15 m，并额外留有认证余量；旧式脱困仍是低速偏移。这会压低狭窄区域的速度，但**不能直接减小安全距离或删除近处真实点来强行过门**。必须先确定机体半径、定位误差和实际跟踪误差。

### 2.5 YOLO 远距离几何过于保守；近处修正有改善但仍不完整

模型给出车的可见正面框；双目视差推算距离。远处视差较小，深度不确定性可能到 5 m。现在又将正面向后外推车体，并加多层余量，多辆车会封死实际上可通过的路线。

已改成距离约 28 m 内使用 LiDAR 点云进行硬碰撞验证，远处 YOLO 体积负责提前预警。若只是远处粗体积堵塞，而近处雷达路段可行，允许先接近到雷达可精化区域。

这能减少“几十米外就停车”，但点云地图、未知空间、真实车身和稳定轨迹切换仍未完整解决。

### 2.6 把 max_speed 改为 40 不等于实际能飞 40

当前启动参数 `cruise_speed=max_speed=40`。实际雷达可见距离约 30 m，结合制动和延迟保护，直路速度常被限制在约 17–18 m/s。上升能力约 4 m/s、下降限制 4.5 m/s；坡度、门洞、避障曲率还会继续限速。

用户要的是简单路况发挥能力，不是一个更高的配置数字。若要进一步提高真实直路速度，需要更远的可信可见范围/地图、已验证的制动能力与延迟模型，而不是只继续抬高 `max_speed`。
