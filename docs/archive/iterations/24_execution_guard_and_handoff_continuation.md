# 2026-10-01：交接续修——执行轨迹验证与规划一致性

承接工作区 `RMUA_避障与速度修复交接_20261001.md`。原交接记录保留；本文记录恢复工作后的代码与验证边界。

## 已落实的修复

1. **过期规划不再直接急停。** `ExecutionGuard` 用最新原始点云检查当前实际位置到执行轨迹的连接段、未来 30 m 路径和当前测得速度的响应段。速度上限包含反应时间、点云年龄和制动距离。点云缺失、过期、为空，或当前响应段撞入净空范围时仍停车。完整搜索忙时保留原执行参考，不能凭旧规划的 `feasible` 直接继续加速。
2. **新旧参考按应用时刻连接。** `JoinedDetour` 从正在执行轨迹的位置、空间一阶和二阶导数连接到候选轨迹；连接段重新检查原始点云。优先较长平滑连接，受近处障碍约束时依次检查 4、2、1 m 连接，未通过则保留原轨迹。这里的 C2 指空间曲线连续，不等于已经完成统一时间参数化或 jerk 验收。
3. **格点末端及回中。** 零偏移终点可达时优先回中；起点导数使用当前参考导数，末端导数为零。不能回中时延续非零终点，后续名义路线清空也必须生成并认证回中曲线，不能直接 `plan=None`。
4. **规划与执行检查同一几何。** run16 暴露出规划体素代表点遗漏限制表面的问题。最终版本保留全部 34 m 内原始点，用 0.2 m 实际偏移曲线检查候选，横向基准方向与执行器一致，公共扫掠采样间距不大于 0.18 m。没有缩小机体净空或删除近点来放行。
5. **制动模型与控制限制对齐。** 执行保护取 `min(lidar_braking, accel, a_down, curve_brake_a)`。当前比赛参数为 `8 / 8 / 5 / 4 m/s²`，因此执行保护用 4 m/s²。这里是配置中的保守模型，仍须通过实测校准；不能将 XYTracker 的默认 4 与比赛实际参数 8 混为一谈。
6. **计算与诊断。** 对车辆包围盒及扫掠查询批量计算，路线查询改为二分定位；完整搜索使用 0.5 秒软预算，预算在候选和格点迭代间检查，单次原生查询及最终认证可能稍超预算。记录提交、开始、完成、读取、实际应用的 monotonic 时间，区分队列时间和搜索时间。遥测含执行轨迹编号、端点偏移/斜率、原始点云验证时间及净空；停车原因区分 `LIDAR_STALE`、`LIDAR_EMPTY`、`EXECUTION_BLOCKED` 和 `BRAKING_OBSTACLE`。

## 离线证据

新工具：`tools/replay_avoidance.py`。例如：

```bash
python3 repo/tools/replay_avoidance.py \
  --run experiments/race_dynamic_15 \
  --out experiments/repair_continuation_20261001/repaired_replay_final.json
```

run15 的 s100–132.5 取到 9 个停车附近样本：

| 指标 | 运行镜像中保留的旧版 | 最终修复版 |
|---|---:|---:|
| 宿主离线完整规划耗时范围 | 395–1171 ms | 227–496 ms |
| 得到完整可行轨迹的样本 | 5 / 9 | 5 / 9 |
| 新短段验证耗时 | — | 约 7–11 ms |

上述独立快照重新求解，不是还原 run15 每一条正在执行的格点曲线，也不能冒充运行时性能。旧版未存完整轨迹；工具以邻近遥测的 XY/垂直命令估计速度，明确标记该限制。

对 run15 已观察到的返程移动窗口、按 `planned_stamp` 去重，共 128 个任务，1296 条采样同时出现“可行、过期、零指令”。该窗口由 s<132.5 截断，**不是已证明有效的官方赛时窗口**；旧录制缺 HUD 状态流，wall 与 pose 时间已有明显偏移。不要把这里的采样数当停车次数或有效比赛 P99。

run16 起点原始点云反例：

`experiments/race_dynamic_16/mission/leg_3_5/clouds/1790838020.621_s0.0.npz`

初版选 `[-1.0,+1.5]`，体素点检查净空约 1.31 m，但执行原始点云检查更小，连接被拒绝。最终版在同一快照选 `[+1.5,+1.5]`，原始点云稠密净空约 1.32 m，连接及执行验证均通过。`+z` 是 NED 向下。该结果仅证明此快照存在一致候选，未证明动态实飞能完整通过车区。

run16 第一阶段的同口径下坡窗口 s1040–1250：用时 21.048 s（run15 20.601），实际进度速度中位数 9.953 m/s（9.514），俯仰变化速率 P95 24.301°/s（24.999），高度误差 P95 0.711 m（0.814），抬头事件仍 2 次，参考坡度反向 0。只覆盖该窗口，不称作全面改善。

run19 同窗口用时 21.336 s，速度中位数 9.293 m/s，俯仰速率 P95 22.845°/s，高度误差 P95 0.549 m，抬头事件 3 次；参考坡度反向 0。总体未证明下坡速度提升。

运行时耗时仍有问题：run19 第一阶段短段验证中位数/P95/最大约 13.8/54.4/198.5 ms；返程观察窗口约 24.4/68.6/290.8 ms。去重后台任务返程 P95 约 850 ms、最大 1261 ms，包含完整任务的回退和调试归档；明显大于宿主离线值。不能将“短段验证”称作已经满足 20 Hz 的实时执行预算。下一步应压缩重复基准采样、隔离归档开销、给近处真实障碍单独的短窗口搜索，并继续审计时钟关系。

run19 在第一次 s≥159.9 前记录到 2344 条零指令采样；许多来自短段净空不足，已不是只因规划年龄停车。正数舍入误差曾使零前视误标成 `BRAKING_OBSTACLE`/`execution_verified=True`；停机后补了 1e-6 m 舍入归零与回归。这是诊断边界修正，未启动新一轮实跑。
